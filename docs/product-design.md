## 一句话定义

续樟是一个以校园可信身份为基础、由智能匹配和 Agent 辅助的信息流通平台。首个生产版本帮助同学发布“我在出”和“我想收”，找到合适的人和物，并以尽可能少的动作完成可信沟通。

平台不是资金中介，也不是把内容无限推给用户的流量产品。它要解决的是：让一条真实需求被正确表达、被合适的人看见、在双方同意的边界内推进，最后留下可理解的结果。

## 沟通的两个模式：留言与连接

聊天不应把技术状态伪装成人的心理状态。产品只展示可验证的传输事实，以及用户主动表达的社交行为；不把“打开页面”“看到通知”或“敲键盘”自动翻译成“已读”“在线”或“准备回复”。

### 留言

留言是异步投递，不附带即时回复义务。目标状态为：

```text
发送中 -> 已发送（消息已持久化到服务器） -> 可选：主动确认
```

“已发送”不声称对方某台设备已经收到；当前协议没有设备 ACK，就不能把服务器提交称为“已送达”。接收端的 `LOCALLY_SEEN` 是设备本地状态，不上传、不广播，也不成为发送方可查询的 `read_at`。收件箱强调“新留言”而不是把人置于“未读债务”中。

接收者可以针对消息主动表达三种明确回应：`received`（收到）、`will_review`（我会看）和 `completed`（已处理）。回应是用户动作，可替换或撤销；回复、引用和普通 reaction 不自动生成回应。

发送者可以表达“普通留言”或“希望今天处理”这类时间尺度，但它不是红色紧急等级，也不获得越过接收方规则的权力。“请求连接”才表示希望现在交流。接收者可以按联系人、时间段和陌生人关系决定哪些请求允许打断；普通留言默认不要求设备立即响起。

### 连接

连接是一次明确请求、接受和结束的实时交流：

```text
请求连接 -> 已连接 -> 已结束
```

`active` 表示双方同意正在进行这次交流，不等于全局在线。进入连接后无需依赖 typing、last seen 或被动已读来证明注意力；结束后再发内容回到留言语义。连接请求必须可被静音、拒绝、限流和按联系人控制，陌生人默认不能用连接请求强行打断。

当前 realtime 不再保存自动/手动已读或 typing 设置；read/typing 路由和事件已删除，旧数据库列在兼容窗口内只作影子保留且不再写入。移动端只维护设备本地 `LOCALLY_SEEN`，服务端公开状态仅为可验证的发送事实和用户主动 acknowledgement；连接隐私通过陌生人开关、busy 截止时间和联系人权限控制。

## 关系空间，而不是无限消息流

[目标态] 一对一沟通的产品母体不是“聊天列表 + 对话框”，而是两个人长期存在的 `Relationship Space`。消息只是空间里的一种事件；连接开始/结束、文件、链接、商品、地点、主动确认、用户标记和共同约定也都是可回到的事件或对象。

```text
Person -> Relationship -> Space -> Events
                                  -> Sessions
                                  -> Shared Objects
                                  -> Memory Rail
```

当前 `Thread / Conversation / Message` 不废弃：`Thread` 先作为关系入口，独立 `Conversation` 继续保存每次留言或连接边界，客户端把现有事实投影成空间与时间轨迹。只有在投影、回放和兼容验证稳定后，才评估引入通用 `SpaceEvent` 写模型，不能为了概念漂亮一次性重写可靠的消息路径。

空间遵循这些交互原则：

- 对方与自己拥有稳定的空间位置；密集阅读时角色缩小，不能挤压正文或无障碍字号。
- 异步时强调历史、标记和共享对象；连接时弱化轨迹，只强调双方明确的“已连接”。
- `Memory Rail` 的基础层来自确定性事实：时间、连接起止、文件、链接、引用、用户 Pin 和结构化对象，不依赖 LLM。
- 可选语义层只能形成带 `source_event_ids` 的摘要、主题或检索入口；AI 是索引，不是事实来源。
- “上一件事说到哪了”先由最近一次连接终点、最近 Pin 和少量末尾事件恢复；模型不可用时仍完整可用。
- 首版轨迹只做“时间 + Pin”。主题聚类、语义回忆和按人物/地点浏览后置。

共享商品、文件、地点或约定不应只是已经滚走的卡片，而应成为双方可以查看、更新或归档的 `Shared Object`。权威价格、商品状态和成交事实仍来自原领域对象；空间只保存经过权限校验的引用或快照，不能把聊天推断升级为业务事实。

## 用户主导的角色化社交分身

[部分实现] 数字分身是用户的身份呈现层，不是平台 Agent，也不是会替用户说话的高拟真数字孪生。产品定义为：**一个由用户主导、AI 可协助生成的角色化社交分身，用来表达身份、边界和接近方式。** 当前 v1 使用受控 token 预览；生成图片、照片风格化和 Provider 资产流程仍后置。

它由四层组成：

1. 外观：统一画风中的发型、轮廓、服装、配饰和色彩；不要求像本人，也不默认性别化或媚宅化。
2. 自我描述：用户主动选择的少量标签，例如慢热、只谈正事或面交友好；系统不得从聊天历史推断并公开人格。
3. 公开接近方式：可留言、可请求连接、忙或稍后等粗粒度状态，只能由用户主动设置或按其明确规则生效。
4. 语义动作：接信、举手请求连接、点头确认或交接物品等低打扰反馈；不能根据 read、typing、online、Push 或后台活动自动变化。

呈现分三级：列表中的小头像、资料页中的完整角色卡、关系空间中的轻量角色。角色在连接前帮助理解“这是谁、怎样接近”；双方真正连接后应弱化，避免把人与人的交流变成角色表演。

点对方角色进入对方资料与双方共同保存的确定性索引；点自己角色查看“我当前向此人展示什么”和联系权限。关系时长、文件数或最近连接只能由原始事件计算，模型生成的关系强度、人格判断或亲密度不得混入资料卡。

校园认证身份与角色外观必须分离。目标态角色卡可以选择“照片风格化”“特征映射”或“完全角色化”，后者明确标注为角色形象；当前 v1 只开放“特征映射”和“角色形象”两种受控模式，任何模式都不等同于真人外貌认证。平台 Agent 使用独立且清楚的视觉语言，用户分身出现绝不意味着 AI 读过或参与了这段沟通。

首版采用统一风格、模板编辑和少量可审核资产，AI 只推荐、补全或生成候选，用户确认后才公开。禁止自动代聊、模仿用户长期对话、好感度、喂养、连续签到和随机搭话；成功标准是更容易理解身份与边界，不是增加停留时长。

## “出”与“收”的哲学

传统二手平台主要围绕“有什么可卖”组织信息，需求方只能反复搜索。续樟把信息流看成两个方向：

```text
出 offer：我拥有某个物品，希望它继续被需要的人使用
收 wanted：我有一个明确需求，希望找到愿意提供的人
```

“出”不是清库存，“收”也不是被动消费。两者都是用户对资源流向的主动声明。系统的职责是降低表达、发现和沟通成本，而不是替用户决定交易。

这个对称结构带来三条产品原则：

1. 首页必须同时容纳出与收，不能把 wanted 降级为搜索失败后的补充表单。
2. 匹配必须双向解释：需求方知道为什么推荐这个物品，提供方知道为什么这条需求值得响应。
3. 成交不是唯一成功结果。一次明确拒绝、需求关闭或避免不合适的联系，同样是在减少信息摩擦。

## 服务对象与身份层级

| 身份 | 可以做什么 | 生产目标 |
| --- | --- | --- |
| 游客 | 浏览公开信息和平台规则 | 不保存个性化画像，不允许联系或发布 |
| 注册用户 | 收藏、管理语言和隐私设置 | 完成基本账号安全校验 |
| 校园认证成员 | 发布出/收、联系、加入校园空间、参与成交 | 通过校园邮箱或学校认可方式验证 membership |
| 校园运营者 | 管理本校园分类、内容和申诉 | 权限限定在所属校园并记录审计 |
| 平台管理员 | 处理跨校园安全、系统配置和重大事件 | 使用强认证、最小权限和不可抵赖审计 |
| Agent | 检索、解释、草拟和在确认后执行动作 | 不拥有独立身份，不得绕过用户和 service 权限 |

[已实现] 当前系统有游客浏览、注册用户、普通用户和全局管理员角色，学校邮箱与学号发现能力已经存在。

[目标态] `CampusMembership` 将账号与校园资格分离。未认证用户可以浏览和收藏，但发布、联系、群组参与和成交意向需要有效校园 membership。

## 用户真正要完成的任务

### 想收物品的人

- 用一句自然语言或表单说明自己要什么、预算多少、最低能接受什么。
- 快速判断匹配结果是否真的满足硬条件。
- 知道推荐来自哪些公开信号，而不是被不透明排序牵着走。
- 用合适的沟通方式联系提供方，并保留拒绝或结束沟通的空间。

### 想出物品的人

- 用图片和少量文字完成可信发布。
- 找到正在寻找类似物品的人，而不是只能等待曝光。
- 在公开程度、联系方式和收款信息上保有控制权。
- 确认线下成交后选择是否自动下架。

### 管理和运营人员

- 看见内容为什么被拦截、谁做了什么管理动作、是否需要人工复核。
- 在不读取无关用户数据的前提下处理举报和申诉。
- 用校园级配置适应不同学校的身份规则和本地政策。

## 核心用户旅程

以下旅程是首个生产版本的主线，也是产品和集成测试的共同基线。

```text
用户表达“想收一台能记笔记的平板，预算 1800”
  -> Agent 识别为 wanted 草稿，不直接发布
  -> 用户确认分类、预算、最低成色和校园范围
  -> 系统发布 wanted 并生成可解释匹配
  -> 另一位同学看到需求，选择自己的 active offer 响应
  -> 需求方在联系人线程中选择实时沟通或留言
  -> 双方自行验货、交接和付款
  -> 卖家确认线下成交，并决定是否自动下架 offer
  -> 需求方关闭 wanted，系统停止继续推荐
```

旅程中的每个箭头都必须有失败路径：没有匹配时允许调整条件，联系被拒绝时不泄露屏蔽关系，Agent 失败时保留手工表单，审核未完成时不公开媒体，成交未确认时不改变商品状态。

## Agent-first，但不是 Agent-only

Agent-first 指用户可以从意图开始，而不是先理解菜单结构。首页允许用户直接说需求，小帮可以将自然语言转为搜索、wanted 草稿或 offer 草稿。

Agent 不应成为必须经过的中间层。所有核心能力必须有可发现的图形界面和可撤销路径：

- 用户可以直接浏览、筛选和填写表单。
- Agent 的推断必须以草稿或推荐原因展示。
- 发布、联系、推荐物品、报价和成交确认前必须让用户看见将发生什么。
- LLM 不可用时，搜索、发布、聊天和线下成交记录仍然可用。

Agent 权限等级和确认协议见 [Agent 系统设计](agent-system.md)。

## 信息流体验原则

### 推荐透明但不喧宾夺主

首页不长期展示“推荐是如何制作的”说明卡片。透明度应体现在具体条目上，例如“符合你的预算”“与你收藏的教材同类”“刚刚发布”，并在设置里提供完整解释和控制。

### 默认降低打扰

- 同一聊天对象在收件箱只出现一个联系人线程。
- 同一商品与同一需求的重复推荐要抑制。
- 通知按用户需要和紧急程度分级，不能把所有事件都当即时提醒。
- 关闭、拒绝和过期的会话保留历史，但不持续占据主要注意力。

### 让不确定性可见

平台应区分用户填写的事实、系统计算的匹配、Agent 推断和管理员结论。界面不能把“模型认为可能合适”显示成“已经符合要求”，也不能把“发起成交意向”显示成“付款成功”。

### 让控制权靠近动作

连接隐私放在设置页，主动 acknowledgement 放在具体消息上，收款码公开开关放在收款码旁，推荐反馈放在具体条目菜单，Agent 确认放在动作预览页。不要用一个难以理解的全局开关代替上下文控制。

## 产品边界

首个生产版本正式支持：

- 校园物品 offer/wanted 发布、搜索、匹配和推荐。
- 收藏、用户主页、发现设置和受控公开的线下收款码。
- 联系人线程、实时会话、留言、群组和频道。
- 线下成交意向、卖家确认和可选自动下架。
- Agent 搜索、解释、草拟，以及确认后的发布和联系动作。
- 内容审核、举报、申诉入口和管理员审计。

首个生产版本明确不支持：

- 平台资金托管、支付确认、结算、物流和赔付承诺。
- Agent 无人监督地报价、议价、公开隐私信息或确认成交。
- 跨校园默认推荐或联系。
- 服务、技能、活动、互助和知识等非物品内容的正式发布。
- 服务器无法解密的生产私聊。

## 成功指标

北极星指标使用“有效信息闭环率”，而不是停留时长：一条 offer/wanted 在有效期内发生合格匹配、双方沟通或由用户明确完成/关闭的比例。

| 指标组 | 建议指标 | 防止什么问题 |
| --- | --- | --- |
| 信息质量 | 发布完成率、字段完整度、审核通过率 | Agent 只追求发布量，产生低质量内容 |
| 匹配质量 | 硬约束满足率、匹配点击率、有效响应率 | 推荐只优化点击而忽略真实适配 |
| 沟通质量 | 首次有效回复时间、骚扰举报率、会话正常结束率 | 用消息量掩盖沟通压力 |
| 身份表达 | 分身完成率、公开边界理解率、被误认成 Agent/真人照片的比例 | 只追求“好看”而牺牲可信度与可理解性 |
| 关系空间 | 找回上次事项成功率、无需滚动即可找到共享对象的比例 | 把 Memory Rail 做成新的信息噪声或 AI 幻觉层 |
| 闭环质量 | wanted 关闭率、成交确认率、重复发布率 | 把未确认意向误当成交 |
| 信任安全 | 审核时延、申诉改判率、管理员越权事件 | 只追求拦截量导致误伤 |
| Agent 质量 | 草稿采纳率、确认取消率、越权执行数 | 用调用次数代替用户价值 |

停留时长、消息数量和通知打开率只能作为诊断指标，不能成为单独优化目标。
