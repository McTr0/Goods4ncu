# 首次上线检查清单

| 项目 | 内容 |
| --- | --- |
| 适用场景 | **第一次**把这个系统部署到真实环境、对真实南昌大学学生开放 |
| 与其他文档的关系 | [运维手册](operations.md)讲日常运行，[生产就绪评估](production-readiness.md)讲门槛是否关闭。本文只讲**第一次**，因为这里列的每一条都只在第一次出现 |

---

## 为什么单独有这份文档

在一天之内，我在"真实学生能不能用"这条路径上找到四个阻断级缺陷。它们有一个共同点，而这个共同点就是本文存在的理由：

> **它们全都只在"第一次真实使用"时出现。之前所有验证都在复用已有状态，所以全都没看见。**

| 缺陷 | 为什么之前看不见 |
| --- | --- |
| 全新数据库上部署起不来 | 每次部署都复用已有库，表都在，清种子脚本不会失败 |
| 入学验证流程从没被跑过 | 部署脚本用 `UPDATE ... SET status='verified'` 抄了近道 |
| 做好的功能没有入口 | 后端接口测试全绿，但 app 里没有任何界面调用它 |
| 限流器故障放大成全站宕机 | Redis 一直是健康的，没人试过它写不出磁盘时会怎样 |

四条里有三条会在上线当天才爆发，而那时候受损的是**第一批真实用户的第一印象**——校园产品几乎没有第二次机会。

所以这份清单的组织原则不是"检查功能是否正常"，而是：**每一条都要求你亲手把某件事做**坏**，然后确认系统的反应是可接受的。**

---

## 一、从零开始，不复用任何状态

**这是最重要的一条。** 用一个**全新的、空的**数据库和一个**全新的** Redis 走完整个部署。

```bash
# 必须是空库，不是清过数据的库
createdb goods4ncu_prod
./scripts/provision_app_role.sh          # 应用角色必须 NOSUPERUSER
goods4ncu migrate                        # 迁移必须先于清种子
psql -d goods4ncu_prod -v ON_ERROR_STOP=1 -f scripts/remove_demo_seed.sql
# 然后才启动应用
```

**顺序不能换**，原因是个死循环：demo 种子账号由迁移创建，而应用在生产模式下只要检测到种子就拒绝启动。所以必须有个东西在应用之前跑迁移——那就是 `goods4ncu migrate` 存在的理由。

**必须验证的**
- [ ] `ON_ERROR_STOP=1` 一定要加。**没有它 psql 会为一个整体失败的脚本返回退出码 0**，于是清理脚本报告成功、应用拒绝启动，而你以为已经清干净了
- [ ] 清理脚本跑完，`SELECT COUNT(*) FROM users WHERE id IN (...)` 必须是 0（脚本自己会校验并抛异常，但你要看到它）
- [ ] 应用能启动。启不来先看日志里有没有 `refusing to start in production: demo seed accounts are present`
- [ ] **再跑一遍清理脚本**，必须成功而不是报错——部署会反复执行它

## 二、亲手走一遍学生要走的路

不要用 SQL 造已验证的用户。**用 SQL 造出来的用户，测的是你的 SQL，不是学生的体验。**

```
注册 → 拿到 pending 成员身份 → 请求校园邮箱验证码
     → 真的收到邮件 → 提交验证码 → 变成 verified
     → 发一条意图 → 和小帮说句话
```

**必须验证的**
- [ ] 用一个真实的 `@email.ncu.edu.cn` 地址注册，**邮件真的到了收件箱**
- [ ] 验证码在 TTL 内可用，过期后不可用
- [ ] 验证前发意图返回 403（`campus_verification_required`）；验证后返回 200
- [ ] 用一个**非** ncu 域的邮箱试一次，必须被拒绝

### 邮件投递是硬依赖

生产模式下 `CAMPUS_VERIFICATION_DELIVERY_URL` 是**必填**，缺了应用直接 panic 退出。它是一个 webhook：

```json
POST <你的地址>
{ "to": "...", "template": "campus_email_verification",
  "code": "123456", "expires_in_seconds": 600 }
```

本仓库里的实现是一个**本地 stand-in**，只把码写进文件供部署脚本读取。**真实上线必须换成能真正发信的东西**（阿里云邮件推送、腾讯 SES、或自建 SMTP 网关的一层适配）。

- [ ] 网关已就位，并且**试过它挂掉的情况**：投递失败时挑战记录写入 `delivery_status='failed'`，接口返回错误，用户看到的是"发送失败请重试"而不是卡在无限等待
- [ ] 也试过它**慢**的情况（不是挂，是 hang）。投递有 10s 超时，故意比路由层 60s 的超时短很多：真等到 60s，整个 handler 会被外层砍掉，`delivery_status='failed'` 那次写入根本跑不到，失败会从运维唯一会看的那张表里消失
- [ ] 投递失败之后**立刻重发是允许的**。60 秒冷却只对真的送到了的那次生效——让学生为一封他没收到的信等一分钟，会把网关抖动变成"我根本注册不了"。每小时上限仍然照算，不分成功失败，否则一个持续报错的网关就成了对着一个邮箱的无限外发

## 三、把依赖一个一个搞坏

这一节是四个缺陷里教训最深的一个。**限流器挂掉曾经让每个请求都返回 429**——唯一职责是"保障高负载下可用"的组件，把整个服务搞挂了。

对每个依赖，拔掉它，然后确认**降级方向是对的**：

| 依赖 | 搞坏的方式 | 可接受的反应 |
| --- | --- | --- |
| Redis | `redis-cli DEBUG sleep 30` 或直接停掉 | 请求**照常服务**（限流放行 + WARN 日志），不是 429 |
| Redis 只读 | `CONFIG SET stop-writes-on-bgsave-error yes` 且让保存失败 | 同上。这正是真实发生过的那次 |
| LLM | 换成无效 key | 小帮降级，商品浏览/搜索/聊天不受影响 |
| 对象存储 | 停掉 MinIO/OSS | 图片不显示，但页面不白屏、能发文字 |
| 邮件网关 | 返回 500 | 验证请求报错可重试，不静默失败 |

**必须验证的**
- [ ] Redis 挂掉时，**登录仍然可用**。这条单独列出来，因为它就是上次的事故形态
- [ ] 每种降级都在日志里留下 WARN 或 ERROR。**静默降级和正常运行长得一样**，这比故障本身更危险
- [ ] Redis 不需要持久化（只存限流计数和 WebSocket 扇出，都能自建），建议直接 `--save ''`。开着快照意味着一次保存失败就变成拒绝写入的实例

## 四、确认功能真的有入口

后端接口测试全绿，不代表用户能碰到它。**我做完了意图层和临时聚合，app 里却没有任何界面调用它们**，真实学生打开看到的还是旧的商品栅格。

**必须验证的**（用真实浏览器/真机，不是 curl）
- [ ] 底部"发布"打开的是**意图输入**，一句话就能提交，不逼填价格
- [ ] "找搭子 / 求帮忙 / 约活动"三类**有可点到的入口**
- [ ] 无价商品提交后，界面**明确说明**它不会出现在商品栅格里
- [ ] 小帮执行低风险操作后，结果旁边有**撤销**按钮且真的能撤销
- [ ] 被自动拉进一个空间后，能看到**为什么是我**

> 判据很简单：**让一个没参与开发的人拿着手机，不给任何提示，看他能不能自己说出一句"我想…"。**

## 五、单 IP 会把自己限流

冒烟测试从一台机器发出，而限流是按 IP 的。真实用户分散在几千个 IP 上，你的冒烟脚本只有一个。

- [ ] 要么给冒烟测试的来源 IP 放宽配额，要么脚本遇到 429 时退避重试
- [ ] **不要因为冒烟测试被限流就永久调高全局配额**——那个配额是在保护你

## 六、上线当天要能回答的问题

这些指标在 `GET /api/admin/community-health?days=1`（管理员，按校园隔离）：

| 指标 | 第一天该看什么 |
| --- | --- |
| **发帖被回应率** | 最重要的一个。第一周低于 50% 说明供给方在对着空气说话 |
| **首次回应时长中位数** | 超过几小时，学生就不会再来第二次 |
| **达成共识所需消息数** | 基线值。后续所有改进都要跟它比 |
| **新人第 7 日留存** | 上线一周后才有样本 |
| **打扰接受率** | 低于 40% 说明推送在消耗信任 |
| **聚合多样性** | 反复把同一批人凑一起 = 校园在碎片化 |

**明确不看**：DAU、发帖量、停留时长。追它们会把产品推回信息流。

- [ ] 上线前先跑一次，确认读数是 0 而不是报错——**空系统和坏接口都返回"没有数据"**
- [ ] 记下第一天的基线值。没有基线，后面所有"改进了"都是错觉

## 七、不可退让的底线

这些在别处也写着，但第一次上线容易被"先跑起来"压过去：

- [ ] 应用数据库角色**不是** superuser（superuser 绕过 RLS，行级隔离会静默失效）
- [ ] `JWT_SECRET` ≥32 字符且不是任何示例值
- [ ] `CORS_ORIGINS` 是显式白名单，不是 `*`
- [ ] 没有任何 demo 种子账号（`Test1234` 是公开的，其中一个还是平台管理员）
- [ ] 已应用的迁移**不可修改**（sqlx 校验 checksum；本项目已因此中断过一次部署）
- [ ] 迁移是**编译期嵌入二进制**的——改了 `migrations/` 必须重新构建，不能复用旧可执行文件
- [ ] 备份和 PITR 演练跑过一次（`scripts/backup_pitr_drill.sh`）

---

## 八、我建议的第一周节奏

上线不是开闸放水。校园产品的冷启动有个硬约束：**临时聚合需要意图密度才能成团**，而密度需要人。

1. **先请二三十个真人**，最好彼此有点关系（一个院、一栋楼），让他们真的想找点什么
2. **每天看一次被回应率**。如果发帖没人理，先别加功能——那是密度问题，不是功能问题
3. **手动触发一次成团**（`POST /api/admin/spaces/form`），别等每小时的扫描。池子薄的时候正是最需要它的时候
4. **成团被拒绝的理由要看**。`too_few` 是正常的（人还不够）；`too_familiar` 反复出现说明圈子在固化
5. **第七天看留存**。这是第一个真正能说明"这地方值不值得回来"的数字

---

## 附：这份清单不能替代什么

它能减少"上线当天才发现"的概率，但它**不能回答"这是不是南昌大学最好的社区"**。那个问题只有真实学生用过之后才有答案，而且答案可能是难听的。

清单的作用是确保：**当他们真的来了，他们遇到的问题是产品问题，不是系统本来就不能用。**
